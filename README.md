# Lumen

Контроллер адресной ленты на ESP32 с декларативным планировщиком и
собственным веб-интерфейсом. Говорит на JSON API, совместимом с WLED, —
за счёт этого Home Assistant находит устройство сам, без custom_component
и без YAML.

Собирается под две платы: **ESP32-C3 Super Mini** и **ESP32 DevKit (WROOM-32)**.

Что внутри: 20 эффектов, 16 палитр, сегменты, пресеты, планировщик с
солнечными якорями, сохранение состояния, mDNS-обнаружение, OTA, бэкап и
восстановление, мобильный интерфейс без единой внешней зависимости.

---

## Быстрый старт

```bash
pio run -e devkit_wroom32 -t upload        # прошивка
pio run -e devkit_wroom32 -t uploadfs      # интерфейс на LittleFS
pio device monitor
```

Для C3 то же самое с `-e supermini_c3`. Окружение `devkit_wroom32` стоит
в `default_envs`, так что для WROOM-32 флаг `-e` можно опускать.

**`uploadfs` обязателен** — без него на устройстве будет только API и
страница-заглушка.

При первом включении поднимается точка доступа `Lumen-XXXX`. Подключаетесь,
открывается портал, вводите сеть и пароль. После перезапуска контроллер
доступен как `http://lumen.local`.

Портал можно и обойти, положив креды в `data/config.json` — тогда они
уедут на устройство вместе с интерфейсом. Подробности и разбор типовых
граблей — в разделе [Заливка и диагностика](#заливка-и-диагностика).

## Тесты

Всё, что проверяется без ESP32 — одной командой:

```bash
scripts/test_all.sh
```

Нужны `g++`, `python3` и `node`. Скрипт сам переходит в корень репозитория,
поэтому запускать его можно из любого каталога.

Три набора:

- **Ядро планировщика** — 48 тестов, включая прогон целого года.
- **Движок эффектов** — каждый эффект × каждая палитра × весь диапазон
  speed/intensity, с байтами-часовыми для отлова записи мимо буфера.
- **Интерфейс** — прогон скрипта в Node со stub-DOM: ловит опечатки в
  идентификаторах и проверяет разбор времени, цветов и меток якорей.

**Без `node` прогон обрывается на третьем наборе с кодом 127** — в скрипте
стоит `set -euo pipefail`. Первые два набора к этому моменту уже отработали,
и их результат виден в выводе, но для CI или pre-commit hook это провал.
Ставится штатно: `sudo apt install nodejs`.

По отдельности:

```bash
# ядро планировщика
g++ -std=c++17 -Wall -Wextra -I lib/schedule lib/schedule/*.cpp \
    test/test_schedule/test_main.cpp -o /tmp/lumen_sched && /tmp/lumen_sched

# движок эффектов
scripts/test_effects.sh

# интерфейс
python3 scripts/extract_ui_js.py /tmp/lumen_ui.js
node test/ui/uitest.js /tmp/lumen_ui.js
```

Окружение `native` в `platformio.ini` объявлено с `test_framework = custom`,
но требуемого файла `test/test_custom_runner.py` в репозитории нет, поэтому
`pio test -e native` падает с `Could not find custom test runner by this path`.
Пользуйтесь командами выше.

## Схема подключения

```
  СИГНАЛ
    ESP32 GPIO ──► 2 (1A)  ┃74AHCT125┃  3 (1Y) ──[330 Ом]──► DIN ленты
         3.3 В                                       5 В

  РАЗРЕШЕНИЕ ВЫХОДА
    1 (1OE) ──► GND          без этого выход отключён (третье состояние)

  ПИТАНИЕ БУФЕРА
    14 (VCC) ──► +5 В        та же шина, что питает ленту
     7 (GND) ──► GND
    100 нФ между 14 и 7, вплотную к корпусу

  НЕИСПОЛЬЗУЕМЫЕ КАНАЛЫ
    5, 9, 12   (2A/3A/4A)     ──► GND
    4, 10, 13  (2OE/3OE/4OE)  ──► +5 В

  ПИТАНИЕ ЛЕНТЫ
    5 V PSU ──┬──► +5 В ленты
              └──► GND ──┬──► GND ленты
                         ├──► GND буфера (вывод 7)
                         └──► GND ESP32        ← всё в одну точку
    1000 мкФ между +5 В и GND у первого диода
```

Схема нарочно записана списком соединений, а не картинкой: у паяльника
важно, что с чем соединено, а красивая ASCII-графика тут только добавляет
поводов прочитать не тот провод.

Пины по умолчанию: **GPIO2** на C3 Super Mini, **GPIO16** на WROOM-32.
Меняются в `data/config.json` или через `POST /api/config`.

### 74AHCT125 — ключ, выводы и что внутри

#### Ключ и нумерация

На корпусе есть **ключ** — полукруглая выемка на короткой стороне, а часто
ещё и точка-углубление рядом с первым выводом. Это единственный ориентир:
сама микросхема симметрична, и без ключа определить, где вывод 1, нельзя.

Держите корпус так, чтобы ключ был **сверху**. Тогда вывод 1 — слева
сверху, дальше номера идут **против часовой стрелки**: вниз по левой
стороне до 7, потом снизу вверх по правой от 8 до 14.

```
                ключ   
              ┌───∪───┐  
    1OE ── 1  │ ●     │  14 ── VCC   → +5 В
     1A ── 2  │       │  13 ── 4OE
     1Y ── 3  │  74   │  12 ── 4A
    2OE ── 4  │ AHCT  │  11 ── 4Y
     2A ── 5  │  125  │  10 ── 3OE
     2Y ── 6  │       │   9 ── 3A
    GND ── 7  │       │   8 ── 3Y
              └───────┘
```

Запомнить проще всего так: **питание всегда по диагонали** — GND на
выводе 7 (внизу слева), VCC на 14 (вверху справа).

Ошибиться тут дорого. Разверните корпус на 180° — и вывод 14 окажется там,
где вы ждёте вывод 1. Вы подадите 5 В на вход и землю на VCC, и микросхема
умрёт сразу. Второй способ ошибиться коварнее: если паяете с **обратной
стороны** платы, зеркалится вся раскладка. Смотрите на ключ с той же
стороны, с которой стоит корпус, а не с той, с которой паяете.

#### Что происходит внутри

В корпусе четыре независимых буфера. У каждого три вывода: вход `A`,
выход `Y` и разрешение `OE`.

Главное, что нужно понимать: **буфер не усиливает входной сигнал — он
создаёт новый.** Вход только сравнивается с порогом, а выход строится
заново из питания микросхемы. Электрически выход и вход не связаны никак,
общее у них только время переключения.

Отсюда всё остальное:

**Почему это сдвигает уровень.** ESP32 выдаёт 3.3 В. Буфер сравнивает их со
своим порогом (2.0 В у TTL-совместимых входов), уверенно опознаёт единицу и
выдаёт на выходе полные 5 В — потому что берёт их из своего VCC. Никакого
преобразования 3.3 → 5 не происходит: происходит «прочитал единицу — выдал
свою единицу».

**Почему буква T обязательна.** У 74AHC125 (без T) вход КМОП-типа, и порог
единицы равен 0.7×VCC, то есть 3.5 В при питании от пяти вольт. Ваши 3.3 В
до него не дотягивают — микросхема будет читать то единицу, то ноль. У
74AHC**T**125 вход TTL-совместимый с порогом 2.0 В, и запас есть. `AHC`,
`HC`, `HCU`, `LS` не подходят. Годные замены: **74HCT125**,
**74AHCT245**, **74HCT245**.

**Почему это вообще нужно ленте.** WS2812 ждёт на входе `DIN` логическую
единицу не ниже 0.7×VDD. При питании 5 В это 3.5 В, а ESP32 даёт 3.3 В.
Часто «работает и так» — потому что под нагрузкой питание ленты проседает
до 4.5 В, и порог опускается до 3.15 В. Стоит поставить блок питания
получше или укоротить ленту — и всё разваливается. Это самая
трудноуловимая неисправность в таких схемах: она зависит от температуры,
длины ленты и партии диодов.

**Что делает `OE`.** Это разрешение выхода, и оно **активно низкое** —
на что указывает черта над названием в даташите (`OE`). Ноль на нём
включает выход, единица переводит выход в третье состояние: не ноль и не
единица, а высокий импеданс, то есть выход просто отключён от линии.

Вывод 1 надо **посадить на землю**. Если оставить его висеть в воздухе,
вход подтянется наводками к чему угодно, и выход будет то работать, то
отключаться. Симптом характерный: лента оживает от прикосновения к плате,
«чинится» перестановкой проводов и ведёт себя по-разному каждое включение.
Это самая частая ошибка со всем семейством 74x125.

**Почему нельзя оставлять висеть неиспользуемые входы.** У КМОП-входа
огромное сопротивление, и висящий вход медленно дрейфует около порога.
Пока он там, оба выходных транзистора приоткрыты одновременно, микросхема
греется и шумит по питанию — а этот шум приезжает в ваш рабочий канал.
Поэтому входы `2A`, `3A`, `4A` (выводы 5, 9, 12) сажают на землю, а их
`OE` (4, 10, 13) — на VCC, чтобы неиспользуемые выходы были отключены.

**Зачем 100 нФ.** В момент переключения выход берёт из питания короткий
импульс тока. Провод до блока питания для такого импульса — это индуктивность,
и напряжение на выводе 14 просядет. Керамика 100 нФ прямо у корпуса работает
локальным запасом заряда. Ставить её надо **вплотную**, в паре миллиметров:
на длинных ножках она бесполезна.

**Зачем 330 Ом.** Провод до ленты — это линия без согласования, и фронт
сигнала отражается от её дальнего конца обратно. Отражение накладывается на
следующий фронт и портит форму импульса. Резистор 220–470 Ом гасит отражение,
но работает это только если он стоит **у источника**, то есть у вывода 3
буфера, а не у ленты.

**Про скорость можно не думать.** Задержка распространения у 74AHCT125 — около
5 наносекунд, а бит WS2812 длится 1250 наносекунд. Запас в двести пятьдесят
раз.

#### Задействуем один канал из четырёх

```
              ┌───∪───┐
    1OE ── 1  │       │  14 ── VCC   → +5 В
     1A ── 2  │       │  13 ── 4OE
     1Y ── 3  │  74   │  12 ── 4A
    2OE ── 4  │ AHCT  │  11 ── 4Y
     2A ── 5  │  125  │  10 ── 3OE
     2Y ── 6  │       │   9 ── 3A
    GND ── 7  │       │   8 ── 3Y
              └───────┘
```

Задействуем один канал из четырёх:

| Вывод | Куда | Обязательно |
|---|---|---|
| 14 (VCC) | **+5 В**, та же шина, что и лента | да |
| 7 (GND) | общая земля | да |
| 1 (1OE) | **на GND** | да — см. ниже |
| 2 (1A) | GPIO ESP32 (данные, 3.3 В) | да |
| 3 (1Y) | через 330 Ом на DIN ленты | да |
| 5, 9, 12 (2A/3A/4A) | на GND | желательно |
| 4, 10, 13 (2OE/3OE/4OE) | на VCC | желательно |

Плюс **керамика 100 нФ между 14 и 7**, физически вплотную к корпусу.

**Питать буфер надо от 5 В, а не от 3.3 В.** Выходной уровень равен
напряжению питания микросхемы. Запитаете от 3.3 В — получите на выходе те
же 3.3 В, ради которых всё и затевалось.

**Ставьте буфер рядом с лентой, а не рядом с ESP32.** Длинным должен быть
провод с сигналом 5 В — он помехоустойчивее; коротким — участок 3.3 В. От
выхода буфера до первого диода желательно не больше 20–30 см.

### Порядок пайки

Что понадобится, кроме микросхемы: **панелька DIP-14** (паять корпус
напрямую можно, но панелька спасает от перегрева и позволяет заменить
микросхему, не выпаивая), керамика **100 нФ**, резистор **330 Ом**,
электролит **1000 мкФ на 10–16 В**, провода — 0.75 мм² на питание и
0.2–0.35 мм² на сигнал.

**1. Панелька.** Впаяйте её ключом в ту же сторону, в которую будете
вставлять микросхему. У панельки тоже есть выемка — совместите.

**2. Перемычки разрешения и неиспользуемых входов.** Их удобнее положить
первыми, пока плата пустая:

- вывод 1 → вывод 7 (включаем наш канал);
- выводы 5, 9, 12 → вывод 7 (неиспользуемые входы на землю);
- выводы 4, 10, 13 → вывод 14 (неиспользуемые выходы отключены).

**3. Керамика 100 нФ** между выводами 14 и 7, максимально коротко.

**4. Питание.** +5 В на вывод 14, земля на вывод 7 — той же шиной, что
питает ленту. Не тяните питание буфера от ESP32.

**5. Сигнал от ESP32.** GPIO → вывод 2. Этот участок делайте коротким.
Земля ESP32 должна приходить в ту же точку, что земля буфера и ленты.

**6. Резистор 330 Ом** одним концом в вывод 3, вторым — в провод, который
пойдёт на `DIN` ленты.

**7. Электролит 1000 мкФ** между +5 В и GND **у первого диода ленты**, а не
у блока питания. Полярность: минус помечен полосой на корпусе.

**8. Лента.** Три провода: +5 В, GND, данные с резистора.

#### Куда именно на ленте

**У ленты есть направление, и это ошибка номер два после ключа.** На
подложке между диодами напечатаны стрелки — сигнал идёт по ним. Подключаться
надо к тому концу, куда стрелки **входят**: там площадка подписана `DIN`
(или `DI`, `IN`). На противоположном конце `DOUT` — если подключиться туда,
не загорится ничего, и схема будет выглядеть полностью исправной.

Если полосы уже нарезаны и подписей не осталось, ориентируйтесь только по
стрелкам.

### Проверка перед первым включением

Делается мультиметром, **микросхема при этом в панельку не вставлена**.
Пять минут здесь дешевле сгоревшего корпуса.

1. **Прозвонка на короткое.** Между выводом 14 и выводом 7 сопротивления
   быть не должно — если прибор пищит, где-то замыкание, ищите его сейчас.
2. **Земля пришла куда надо.** Прозвоните вывод 7 с землёй блока питания,
   землёй ESP32 и землёй ленты. Все четыре точки должны звониться между
   собой.
3. **Разрешение посажено.** Вывод 1 звонится с выводом 7.
4. **Резистор на месте.** Между выводом 3 и `DIN` ленты — около 330 Ом.
5. **Подайте питание без микросхемы** и измерьте напряжение прямо на
   контактах панельки: между 14 и 7 должно быть 4.8–5.2 В. Если там 3.3 —
   вы запитали буфер не от той шины.
6. **Снимите питание**, вставьте микросхему ключом в правильную сторону,
   включайте.

Порядок подачи питания: сначала лента и буфер, потом ESP32 — или всё
одновременно от одного блока. **Не подключайте ленту под напряжением**: ток
пойдёт через защитные диоды входа `DIN` и выбьет первый пиксель.

### Питание

WS2812B на полной яркости белым потребляет ~60 мА на диод — по 20 мА на
каждый из трёх кристаллов. Отсюда бюджет:

| Диодов | Пик (белый 100%) | Практический БП |
|---|---|---|
| 60 | 3.6 А | 5 В 4 А |
| 144 | 8.6 А | 5 В 10 А |
| 300 | 18 А | 5 В 20 А |
| 1200 | 72 А | несколько БП, секциями |

Реальное потребление на цветных эффектах в 2–3 раза ниже пикового, но
блок питания считают по пику: иначе первый же `Solid` белым уронит
напряжение, и лента уйдёт в мерцание и перезагрузки контроллера.

- **Электролит 1000 мкФ** между +5 В и GND у первого диода, на напряжение
  не ниже 10 В. Гасит бросок тока при включении, который иначе выбивает
  первый пиксель. Полярность соблюдать.
- **Инжекция питания** каждые 100–150 диодов: +5 В и GND подводятся к
  ленте дополнительными проводами прямо от блока питания. Без неё дальний
  конец уходит в красноту — падает напряжение, синий кристалл гаснет первым.
- **Сечение проводов** по питанию — от 0.75 мм² (18 AWG) на магистраль.
  На тонких проводах вся экономия уходит в нагрев и просадку.
- **Предохранитель** по 5 В, номиналом под блок питания.
- **Общая земля.** Земля ESP32, земля буфера и земля ленты — одна точка.
  Без этого сигнал данных не имеет опорного уровня, и лента ведёт себя
  случайным образом даже при идеальной остальной схеме.
- **Не подключайте ленту под напряжением.** При горячем подключении ток
  идёт через защитные диоды входа DIN и выбивает первый пиксель.

Если ESP32 питается от того же блока, подавайте 5 В на вывод `5V`/`VIN`
(не на `3V3`) и берите питание у начала ленты, а не у дальнего конца.

### Выбор GPIO

Пины по умолчанию проверены, но если нужен другой:

**WROOM-32.** Свободно: 4, 5, 13, 17, 18, 19, 21, 22, 23, 25, 26, 27.
Нельзя: 6–11 (заняты SPI-флешем), 34–39 (только вход). Нежелательно:
0, 2, 12, 15 — strapping-пины, состояние на старте влияет на режим
загрузки. На модулях WROVER заняты ещё 16 и 17 — там под PSRAM.

**C3 Super Mini.** Свободно: 0, 1, 3, 4, 5, 6, 7, 10. Осторожно: 2, 8, 9 —
strapping. Штатный GPIO2 из этой группы, и это допустимо ровно потому, что
он нагружен на высокоомный вход буфера. Если решите подключать ленту
напрямую, без 74AHCT125, — переезжайте на другой пин: вход DIN подтягивает
линию и может сорвать загрузку.

Вывод данных идёт через периферию RMT (`NeoEsp32Rmt0Ws2812xMethod`).
Она не боится джиттера от прерываний Wi-Fi, в отличие от программного
bit-bang, — поэтому лента не мерцает при сетевой активности.

## Заливка и диагностика

Развёрнутая версия «Быстрого старта» — с тем, что происходит, когда всё
идёт не гладко.

### Какая у вас плата

Определяется по имени порта, гадать не нужно:

| Порт | Плата | Окружение |
|---|---|---|
| `/dev/ttyUSB*` | DevKit WROOM-32 (UART-мост) | `devkit_wroom32` |
| `/dev/ttyACM*` | C3 Super Mini (USB-CDC) | `supermini_c3` |

Список портов — `pio device list`. Пользователь должен состоять в группе
`dialout`, иначе порт не откроется; `sudo` при этом не нужен нигде.

### Порядок

```bash
scripts/test_all.sh                        # 1. тесты, секунда, без железа
                                           # 2. проверить data/config.json
pio run -e devkit_wroom32                  # 3. сборка, посмотреть на % flash
pio run -e devkit_wroom32 -t upload        # 4. прошивка
pio run -e devkit_wroom32 -t uploadfs      # 5. интерфейс + конфиг
pio device monitor -e devkit_wroom32       # 6. монитор, затем RESET на плате
curl -s http://lumen.local/json/info       # 7. проверка
```

Шаги 4 и 5 независимы, порядок между ними любой.

**На шаге 3** смотрите на процент flash: знаменатель — это раздел `app0`
из `partitions_4mb.csv`. Если он подберётся к 100%, заливка провалится уже
на записи, и узнать об этом лучше здесь.

**На шаге 4**, если плата не заходит в режим загрузки (`Failed to connect
to ESP32: Wrong boot mode detected`), — зажать **BOOT**, коротко нажать
**EN**, отпустить BOOT и сразу запустить команду. На части клонов DevKit
автосброс через DTR/RTS не срабатывает.

### config.json вместо портала

Прошивка читает `/config.json` при старте, поэтому креды можно положить в
образ заранее и не проходить портал вообще. Файл кладётся в `data/`:

```jsonc
{
  "name": "Lumen",
  "wifi": { "ssid": "…", "pass": "…" },
  "led":  { "count": 60, "pin": 16, "bootBri": 128 },
  "loc":  { "lat": 52.2297, "lon": 21.0122,
            "tz": "CET-1CEST,M3.5.0,M10.5.0/3" }
}
```

Поля те же, что пишет `saveConfig()`. `pin` — 16 на WROOM-32, 2 на C3.
`count` обязательно поправьте под свою ленту: меньше реального — хвост
останется тёмным. От `loc` считаются восход и закат для солнечных якорей,
по умолчанию там Варшава.

Файл в `.gitignore` — пароль от Wi-Fi в репозиторий не попадает.

### uploadfs стирает раздел целиком

Он не докладывает файлы, а перезаписывает всю файловую систему образом из
`data/`. Отсюда два следствия.

**Хорошее:** креды из `data/config.json` восстанавливаются при каждой
заливке, и в портал вы больше не проваливаетесь.

**Плохое:** всё, что настроено через веб-интерфейс — расписание, пресеты,
текущий свет — пропадает, потому что в `data/` этого нет. Перед повторным
`uploadfs` снимайте бэкап; он покрывает все три файла, но не настройки
самого устройства:

```bash
curl http://lumen.local/api/backup -o backup.json
# …uploadfs…
curl -X POST http://lumen.local/api/backup \
     -H 'Content-Type: application/json' -d @backup.json
```

Обычный `upload` раздел данных не трогает — конфиг и пресеты перепрошивку
переживают.

### Монитор молчит — это норма

Две отдельные причины, обе штатные.

**Баннер печатается один раз**, через 300 мс после старта. Подключившись к
уже работающему устройству, вы увидите пустой экран. **Нажмите EN (RST) на
плате, не закрывая монитор** — тогда пойдёт вывод загрузчика ROM и следом:

```
Lumen 0.1.0 (wroom32)
Рендер вынесен на ядро 0
```

**Дальше тишина, и это правильно.** В `platformio.ini` стоит
`CORE_DEBUG_LEVEL=2` (WARN), поэтому все `log_i` вырезаны компилятором:
строк `Подключено: <ip>, RSSI`, `mDNS: http://lumen.local` и `OTA доступно`
в бинарнике физически нет. Работающее устройство молчит по построению.
Нужен разговорчивый лог — соберите с `-D CORE_DEBUG_LEVEL=3`.

Если после RESET по-прежнему пусто, дело почти всегда в DTR/RTS: на части
клонов эти линии держат чип в сбросе. Лечится в секции `[common]`:

```ini
monitor_dtr = 0
monitor_rts = 0
```

Полезный факт для диагностики: если `upload` проходит, значит порт, кабель
и мост исправны в обе стороны — проблема не в железе.

### Что печатается, когда что-то не так

| Строка | Причина |
|---|---|
| `Не удалось подключиться к «SSID» — поднимаю портал` | опечатка в пароле, сеть на 5 ГГц, слабый сигнал |
| `Сеть не настроена — поднимаю портал` | `config.json` не прочитался: забыт `uploadfs` или пустой `wifi.ssid` |
| `LittleFS не смонтирован` | раздел данных битый, нужен `erase` |
| `config.json повреждён: …` | синтаксическая ошибка JSON |
| `Не удалось инициализировать ленту` | неверный `led.pin` или недоступный GPIO |

**Появилась точка `Lumen-XXXX`** — значит подключиться не удалось и поднялся
портал. Подключитесь к ней и откройте `http://192.168.4.1`. IP в панели
роутера при этом будет показывать протухшую аренду, за которой уже никого
нет, — по нему не диагностируйте.

**`lumen.local` не резолвится**, а устройство в сети — mDNS проходит не
через все роутеры и не в гостевых сетях. Работайте по IP.

### Обновление по воздуху

После первой удачной заливки провод не нужен:

```bash
pio run -e devkit_wroom32 -t upload \
        --upload-port lumen.local --upload-protocol espota
```

В `platformio.ini` этих параметров нет — передавайте флагами или заведите
отдельное окружение.

**По умолчанию OTA без пароля** — перепрошить контроллер может любое
устройство в локальной сети. Прошивка пишет об этом предупреждение в лог
при каждом запуске. Задать пароль:

```bash
curl -X POST http://lumen.local/api/config \
     -H 'Content-Type: application/json' -d '{"apiPass":"ваш-пароль"}'
```

После перезапуска пароль спрашивается и при OTA (`--auth=ваш-пароль`), и на
изменяющих ручках `/api/*`. Совместимые с WLED `/json/*` остаются открытыми —
интеграция Home Assistant про пароли не знает, и закрыв их, вы сломаете
именно то, ради чего затевалась совместимость.

Лента во время обновления не гасится, так что картинка порвётся.

### Полный сброс

```bash
pio run -e devkit_wroom32 -t erase
```

Нужен редко: при смене таблицы разделов, при `LittleFS не смонтирован`,
которое не лечится обычным `uploadfs`, или если конфиг превратился в мусор.
Стирает всю флеш, включая раздел `nvs` с копией настроек Wi-Fi от
`WiFi.persistent(true)`. После `erase` обязательны оба шага — и `upload`,
и `uploadfs`.

Две вещи, о которые легко споткнуться при правке разделов:

- В `partitions_4mb.csv` раздел данных называется `spiffs`, хотя формат
  внутри LittleFS. Так и надо — Arduino-библиотека ищет раздел по этой
  метке. Переименуете — файлы перестанут находиться, без ошибки в логе.
- Не убирайте `board_build.filesystem = littlefs` из `platformio.ini`:
  по умолчанию PlatformIO соберёт образ SPIFFS, прошивка смонтирует
  LittleFS, и симптом будет тот же — тихо пустая файловая система.

## Интерфейс

Один файл `data/www/index.html`, 40 КБ (13 КБ после gzip). Ни сборки, ни
node_modules, ни CDN — на устройстве в локальной сети внешние ресурсы всё
равно недоступны.

Четыре вкладки: **Свет**, **Расписание**, **Пресеты**, **Настройки**.
Вкладки внизу экрана — там, где до них дотягивается большой палец.

Две вещи, ради которых стоило писать свой UI, а не брать чужой:

**Интерфейс подсвечивается цветом ленты.** Акцент во всём макете —
переменная `--glow`, которая берётся из текущего цвета сегмента. Крутите
цвет — вместе с лентой меняются слайдеры, активные чипы и индикатор.

**Лента суток на вкладке расписания.** Семь горизонтальных полос, по одной
на день недели, каждая — сутки от 00:00 до 24:00. Подложка построена не
из абстрактного градиента, а из реальных восхода и заката для ваших
координат: ночь, рассветные сумерки, день, закатные сумерки. Поверх
рисуются окна правил. Сразу видно, почему правило «за 30 минут до заката»
летом начинается в девять вечера, а зимой — в три часа дня, и как окна
накладываются друг на друга.

Состояние приходит по WebSocket. Слайдеры схлопывают события в один запрос
раз в 60 мс — иначе очередь AsyncWebServer переполняется за пару секунд
активного крутения.

## Home Assistant

Настраивать не нужно ничего. Устройство анонсирует mDNS-сервис
`_wled._tcp.local.` — именно его слушает встроенная интеграция WLED.
Через минуту после включения HA покажет его в *Настройки → Устройства и
службы* как обнаруженное.

Что важно знать про эту интеграцию:

- Она требует прошивку 0.14.0 или новее, поэтому `/json/info` отдаёт
  `"ver": "0.15.0"`. Собственный номер Lumen лежит рядом, в поле `"lumen"`.
- Имена сегментов игнорируются: в HA они всегда «Segment 1», «Segment 2».
- Мастер-контроля над всеми сегментами разом у интеграции нет.

Расписание исполняется **на устройстве**. Если сервер с Home Assistant
выключится, лента продолжит жить по графику.

## Планировщик

Правило описывает **интервал**, а не момент времени. Резолвер отвечает на
вопрос «какое правило действует прямо сейчас», а не «какое событие только
что произошло».

Практическая разница: контроллер перезагрузился в 19:00, внутри окна
18:00–23:00. Событийная модель уже пропустила своё «включить в 18:00» и
оставит ленту тёмной. Резолвер посчитает состояние заново и восстановит
нужную яркость — вместе с позицией внутри fade-огибающей.

```jsonc
{
  "id": 1,
  "enabled": true,
  "priority": 0,
  "from": { "type": "sunset", "value": -30 },   // за 30 мин до заката
  "to":   { "type": "clock",  "value": 1410 },  // 23:30 в минутах
  "days": 127,                                  // битовая маска, бит 0 = вс
  "except": ["2026-12-25"],                     // календарные исключения
  "action": { "preset": 3, "bri": 180, "powerOff": false },
  "fadeIn": 1800,
  "fadeOut": 900
}
```

Что умеет ядро:

- якоря на часах, восходе и закате со смещением в обе стороны;
- окна через полночь (22:00 → 06:00) — дни недели проверяются по дню
  **начала** окна;
- приоритеты: правило «вечеринка» перебивает фоновое, не отменяя его;
- ужимание фейдов, если они не помещаются в окно;
- отказ срабатывать, пока время не синхронизировано с NTP.

Восход и закат считаются на устройстве по алгоритму NOAA из координат —
сети для этого не нужно. Для Варшавы расхождение с реальностью в пределах
минуты (21 июня: 04:14 / 21:01, 21 декабря: 07:43 / 15:25).

Перенос на летнее время берёт на себя POSIX TZ-строка
(`CET-1CEST,M3.5.0,M10.5.0/3` для Польши) — таблицы правил в прошивке нет.

Пресет из правила применяется **один раз, в момент смены правила**. Иначе
он затирал бы ручные правки раз в секунду и покрутить цвет было бы
невозможно.

Залить пример:

```bash
curl -X POST http://lumen.local/api/schedule \
     -H 'Content-Type: application/json' \
     -d @examples/schedule.example.json
```

## Эффекты

| # | Название | Что делает |
|---|---|---|
| 0 | Solid | ровная заливка цветом или палитрой |
| 1 | Blink | мигание, скважность от насыщенности |
| 2 | Breathe | плавное «дыхание» по синусу в квадрате |
| 3 | Wipe | заливка бегущим фронтом и стирание обратно |
| 4 | Rainbow | радуга вдоль ленты, плотность от насыщенности |
| 5 | Twinkle | случайные вспышки с плавным появлением |
| 6 | Chase | бегущий блок по фону |
| 7 | Comet | голова с экспоненциальным хвостом |
| 8 | Fire | шум с интерполяцией поколений, низ горячее верха |
| 9 | Scanner | «глаз Ларсона», треугольная волна с разворотом |
| 10 | Theater | каждый третий диод, шаг по кругу |
| 11 | Colorloop | вся лента одним цветом, оттенок по кругу |
| 12 | Plasma | сумма двух бегущих синусов разной частоты |
| 13 | Noise | шум с интерполяцией по ленте и по времени |
| 14 | Meteor | голова с рассыпающимся следом |
| 15 | Ripple | круги на воде, до четырёх одновременно |
| 16 | Rain | падающие капли с коротким хвостом |
| 17 | Gradient | палитра вдоль ленты, медленно ползёт |
| 18 | Wave | бегущая волна яркости |
| 19 | Sparkle | резкие искры поверх приглушённой основы |

Порядок в списке — это индекс `fx` в API. Только добавлять в конец: иначе
сломаются сохранённые пресеты и автоматизации Home Assistant.

Все двадцать — чистые функции от времени, без состояния между кадрами.
«Случайность» в Twinkle, Fire, Meteor, Ripple, Rain и Sparkle —
детерминированный хеш от `(индекс, поколение)`. Отсюда: рендер можно
вызвать для произвольного `t`, эффекты тестируются без железа, а
перезагрузка не рвёт анимацию посередине.

Эффекты вроде «метеора с рассыпающимся следом» или «кругов на воде» обычно
пишут через буфер, переживающий кадр. Здесь они выражены через поколения:
момент рождения круга и точка его старта считаются из времени и хеша, а не
запоминаются. Свойство «отрисуй мне кадр за любое `t`» того стоит.

### Палитры

Шестнадцать штук: **Default** (берёт цвет сегмента), **Rainbow** (круг HSV),
и четырнадцать градиентных — Party, Ocean, Forest, Lava, Cloud, Heat, Sunset,
Aurora, Ice, Candle, Autumn, Sakura, Neon, Deep.

Градиент задаётся опорными точками `{позиция 0..255, r, g, b}` с линейной
интерполяцией между ними. Формат совпадает с градиентными палитрами FastLED
(MIT), поэтому оттуда их можно переносить как есть. Из WLED палитры не
копируются — он под EUPL-1.2.

Интерфейс рисует превью по данным прошивки: опорные точки отдаёт
`GET /api/palettes`. Своей копии палитр в `index.html` нет — добавляете
палитру, правите только `src/led/effects.cpp`.

## API

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/json` | состояние, info, эффекты, палитры |
| GET | `/json/state` | только состояние |
| GET | `/json/info` | версия, железо, uptime, free heap |
| POST | `/json/state` | управление (совместимо с WLED) |
| GET | `/presets.json` | все пресеты целиком |
| GET | `/api/presets` | список: номер и название |
| DELETE | `/api/presets?id=N` | удалить пресет |
| GET | `/api/schedule` | текущее расписание |
| POST | `/api/schedule` | заменить расписание целиком |
| GET | `/api/status` | время, TZ, солнце, активное правило |
| GET | `/api/config` | настройки устройства (без пароля Wi-Fi) |
| POST | `/api/config` | изменить настройки |
| GET | `/api/backup` | выгрузить расписание, пресеты и состояние одним файлом |
| POST | `/api/backup` | восстановить из бэкапа |
| POST | `/api/reboot` | перезапуск |
| WS | `/ws` | состояние в реальном времени |

Изменяющие ручки `/api/*` закрываются паролем, если он задан полем
`apiPass` в `POST /api/config`. Пустой пароль — защиты нет, так работает
первый запуск. `/json/*` не закрываются никогда: их читает Home Assistant.
`GET /api/config` пароль наружу не отдаёт, только флаг `authSet`.

`GET /json/info` отдаёт живые `fps` и `pwr` — второе это оценка
потребления в мА по текущему кадру, из расчёта 20 мА на кристалл. Прикидка
для интерфейса, а не измерение.

```bash
# включить радугу на полной скорости
curl -X POST http://lumen.local/json/state \
     -H 'Content-Type: application/json' \
     -d '{"on":true,"bri":200,"seg":[{"id":0,"fx":4,"sx":255,"pal":1}]}'

# сохранить текущий свет как пресет 3
curl -X POST http://lumen.local/json/state \
     -H 'Content-Type: application/json' \
     -d '{"psave":3,"n":"Вечер"}'

# применить пресет 3
curl -X POST http://lumen.local/json/state \
     -H 'Content-Type: application/json' -d '{"ps":3}'
```

```
  schedule.{h,cpp}        резолвер интервалов и огибающих
test/test_schedule/     48 тестов ядра, включая прогон целого года
test/ui/uitest.js       прогон интерфейса в Node со stub-DOM
src/
  core/state.*            состояние под мьютексом
  core/presets.*          сцены в presets.json, чтение по требованию
  core/scheduler_runner.* мост: NTP, TZ, координаты → ядро → лента
  led/effects.*           12 эффектов и 6 палитр
  led/led_controller.*    NeoPixelBus, сегменты, гамма-коррекция
  net/wifi_provision.*    подключение и captive-портал
  net/discovery.*         mDNS `_wled._tcp`
  net/web_server.*        HTTP + WebSocket + весь API
  net/ota.*               обновление по воздуху
  store/store.*           config.json и schedule.json на LittleFS
test/effects/           smoke-тест движка эффектов
data/www/index.html     интерфейс, заливается через uploadfs
data/config.json        необязательный: креды Wi-Fi и настройки в обход портала
examples/               пример расписания

.claude/skills/         правила проекта для Claude Code
```

Ядро планировщика намеренно не знает ни про Arduino, ни про `time()`: на
вход подаются дата, минута суток и солнечные времена. Поэтому год
виртуального времени прогоняется тестом за долю секунды, а краевые случаи
(переход на летнее время, окна через полночь, полярная ночь) ловятся на
хосте, а не на столе с осциллографом.

## Различия между платами

| | C3 Super Mini | DevKit WROOM-32 |
|---|---|---|
| Ядра | 1 (RISC-V) | 2 |
| Рендер | в основном цикле | отдельная задача на ядре 0 |
| Диодов по умолчанию | 300 | 1200 |
| Сегментов | 4 | 16 |
| Serial | USB-CDC | UART-мост |

У большинства клонов C3 Super Mini слабая антенна из-за разводки платы:
держите его в прямой видимости роутера. `WiFi.setSleep(false)` в прошивке
уже стоит — без него задержки HTTP на C3 доходят до сотен миллисекунд.
